## Module 1 — Understanding Claude

### 1.1 What Claude actually is (full depth)

**Explanation.** Claude is a Large Language Model: a neural network trained to predict the next
token given everything before it. There's no persistent "brain" between turns — every response is
generated by re-reading the whole conversation and predicting forward.

```
┌─────────────────────────────────────────────┐
│               CONTEXT WINDOW                 │
│ [System Prompt] ← rules, persona, tools      │
│ [User 1] → [Assistant 1] → [User 2] → ??? ←gen now
└─────────────────────────────────────────────┘
```

**Why it matters.** If you model Claude as "context → next tokens," you debug correctly: when
output is wrong, ask "what was actually in context?" not "is the model broken?"

**Enterprise example.** A PR-reviewer bot "forgot" a coding standard from message 1 of a 40-message
thread — it was still in context, just diluted by noise. Fix: re-inject the standard near the end
of context before every review call.

**Live example — the raw request shape:**
```json
{
  "model": "claude-sonnet-4-6",
  "max_tokens": 1024,
  "system": "You are a senior backend engineer. Be terse and technical.",
  "messages": [
    { "role": "user", "content": "Explain idempotency keys." },
    { "role": "assistant", "content": "An idempotency key is..." },
    { "role": "user", "content": "Show a Postgres schema for storing them." }
  ]
}
```

**Common mistakes:** assuming memory persists across separate chats without explicit
retrieval/memory systems; assuming longer threads are always better (they often degrade quality);
treating hallucination as a patchable bug instead of an inherent property of prediction under
uncertainty.

**Best practices:** keep system prompts stable/authoritative; restate critical constraints in long
threads; never rely on implicit cross-session memory unless you built retrieval for it.

**Exercise:** Explain, in your own words, what happens (and why) if you open a brand-new chat and
ask "what did I ask you yesterday?"

**Interview question:** "Why can a model 'forget' something that's technically still in its
context window?"

### 1.2 Tokens & the Context Window

- **Tokens** are the model's unit of text — roughly ¾ of a word in English (`"internationalization"`
  → several tokens; `"cat"` → one). Code, especially with unusual identifiers, tokenizes less
  efficiently than prose.
- **Context window** = the maximum tokens (input + output) a single request can hold. Current
  Claude models support very large windows (hundreds of thousands of tokens), but *usable* context
  — where retrieval and reasoning stay sharp — is often smaller than the technical max, especially
  as unrelated content accumulates.
- **Enterprise implication:** dumping an entire monorepo into context is rarely the right move.
  Retrieval (grep/search first, then load only relevant files) beats brute-force context stuffing —
  this is the seed of the RAG discussion in Module 12.
- **Cost implication:** input and output tokens are billed separately (output costs more per
  token). A prompt that re-sends a large document every turn is far more expensive than one that
  references a cached or externally stored version.
- **Mistake to avoid:** pasting huge logs/stack traces "just in case." Extract the relevant slice.

### 1.3 Reasoning, System/User/Assistant roles

- **System prompt:** sets persistent rules, persona, and constraints for the whole conversation.
  In enterprise use, this is where you encode "you are reviewing against our internal style guide,"
  tool access, and non-negotiable constraints.
- **User prompt:** the task/question for this turn.
  **Assistant prompt:** Claude's own prior turns — also part of context, and can be pre-seeded
  (e.g., to few-shot a desired response style).
- **Reasoning/extended thinking:** for hard multi-step problems, letting the model reason step by
  step before the final answer improves correctness on math, planning, and multi-constraint tasks.
  Enterprise pattern: use it for architecture trade-off analysis and root-cause debugging, skip it
  for simple lookups (it costs latency/tokens).

### 1.4 Memory & context management

Claude has no built-in cross-session memory at the raw API level. What looks like "memory" in a
product surface (like claude.ai) is a specific engineered feature — retrieval of saved facts
injected into context — not a change to the underlying model. For enterprise systems, "memory" is
something *you* architect: a database/vector store you query and inject, not something the model
does automatically.

### 1.5 Strengths, limitations, hallucinations

**Strengths:** synthesis across long documents, code generation/explanation, following complex
multi-constraint instructions, structured output (JSON/XML), tool use/agentic workflows.

**Limitations:** no guaranteed access to information after training (needs search/tools for
current facts), can be confidently wrong on obscure or highly specific factual claims, sensitive
to prompt ambiguity, no true persistent state.

**Hallucination, practically:** highest risk on (a) very specific factual claims with no source
in context, (b) citing exact code line numbers/APIs from memory instead of the actual repo, (c)
math/counting without explicit step-by-step work. Mitigation: give it the source material, ask it
to cite from context, and for code, have it actually read the files rather than recall them.

### 1.6 Cost, performance, model versions

Anthropic ships multiple model tiers trading off capability vs. cost/latency (a fast/cheap tier for
simple, high-volume tasks; a mid-tier balancing both; a top tier for hard reasoning/agentic work).
**Enterprise rule of thumb:** route by task complexity — classification/formatting/simple
extraction → cheapest capable model; multi-step coding, architecture, and ambiguous judgment calls
→ the strongest model. Because exact current model names, prices, and context limits change
over time, verify against `docs.claude.com` before quoting numbers in a real proposal — don't
memorize this once and treat it as permanent.

## Module 2 — Claude Platform

*(Anthropic's product surface changes frequently — treat specifics here as "how it generally
works," and check `support.claude.com` / `docs.claude.com` for exact current UI and limits.)*

- **Chats:** single conversation threads; each is its own context window.
- **Projects:** a persistent workspace that bundles project-level instructions plus a knowledge
  base of uploaded reference docs — every chat inside inherits that context automatically. Use for
  a recurring body of work (e.g., "our API style guide + spec docs" for an ongoing service).
- **Artifacts:** a separate rendering pane for substantial generated content (code, documents,
  interactive apps) — keeps large outputs out of the main chat flow and lets you iterate on one
  piece of content across turns.
- **Knowledge/Uploads:** documents, PDFs, images, spreadsheets you attach for Claude to read
  directly — grounding answers in *your* material instead of training data.
- **Vision/PDF analysis:** Claude can read images and PDFs natively (diagrams, screenshots, scanned
  docs) — useful for architecture diagram review or reading a legacy design doc that only exists
  as a PDF.
- **Web search / code execution:** built-in tools that let Claude fetch current information or run
  code to verify its own output rather than guessing.
- **Integrations/Connectors (MCP-based):** connects Claude to external systems — GitHub, Google
  Drive, Slack, and others — so it can read real tickets, docs, and repos instead of you
  copy-pasting them in.
- **Claude Team/Enterprise:** adds org-level admin — user provisioning, shared projects, audit
  logs, data retention controls, SSO — the governance layer needed to run Claude across a company
  rather than as an individual tool.
- **API keys, rate limits, billing, usage monitoring:** live under the Console for developers
  building on the API directly, separate from the consumer chat UI — rate limits and pricing are
  tier- and model-dependent and change over time, so confirm current numbers before budgeting.

**Enterprise workflow tie-in:** a typical setup is one Project per service/repo, with the service's
architecture doc, style guide, and key specs as Knowledge, so every engineer's chat about that
service starts from the same grounded context instead of everyone re-explaining it from scratch.

## Module 3 — Prompt Engineering

Core techniques, condensed:

| Technique | What it is | When to use |
|---|---|---|
| Zero-shot | Direct instruction, no examples | Simple, well-understood tasks |
| Few-shot | 2–5 examples of desired input→output | Consistent formatting/style needed |
| Chain of Thought | Ask the model to reason step-by-step before answering | Multi-step logic, math, debugging |
| Role prompting | "You are a senior X" | Calibrates tone/depth, not magic — pair with explicit constraints |
| Constraint prompting | Explicit hard rules ("never do X", "must include Y") | Compliance-sensitive or format-critical output |
| Structured prompting (XML/Markdown/JSON) | Wrap inputs/instructions in tags or schemas | Long/complex prompts; makes sections unambiguous |
| Persona prompts | Consistent voice/expertise across a session | Customer-facing content, docs |
| Planning prompts | Ask for a plan before execution | Multi-file changes, large features |
| Self-review/critique/verification prompts | Ask the model to check its own output against criteria | High-stakes code/content before it ships |
| Agentic prompting | Give a goal + tools, let the model decide steps | Automating multi-step workflows |
| Prompt chaining | Output of prompt A feeds prompt B | Breaking a big task into verifiable stages |

**Enterprise prompt standards (what senior teams actually do):**
- Version-control prompts like code (a `/prompts` folder in the repo, PR-reviewed).
- Every production prompt has a docstring: purpose, expected input, expected output shape, owner.
- Prompts get **tested** against a small eval set before shipping (see Module 11), not just
  eyeballed once.

**Common failure mode:** vague role + vague ask ("You're an expert. Make this better.") — better:
explicit target, constraints, and a definition of "done" ("Rewrite this function to reduce
allocations; keep the public signature; add a comment only where non-obvious; return only the
diff.").

## Module 4 — Claude for Software Engineering

Claude is language/framework-agnostic — the leverage comes from *how* you use it, not which stack.
Patterns that hold across Java/Spring, Python, Node, React/Angular/Vue, SQL/NoSQL, Docker/K8s,
cloud (AWS/Azure/GCP), CI/CD, Kafka/RabbitMQ, auth (OAuth/JWT), and testing frameworks:

1. **Ground it in real code, not memory.** For an existing codebase, have Claude read the actual
   files (via Claude Code, an upload, or a connector) rather than asking it to recall "how Spring
   Boot validation usually works" — framework APIs and your specific version/config matter.
2. **Ask for a plan before a diff** on anything touching more than one file — catches wrong
   assumptions before they're baked into code.
3. **Use it for the boring-but-risky work** senior engineers value most: writing thorough test
   cases (including edge cases you'd forget), explaining unfamiliar code before you touch it,
   drafting migration scripts with rollback plans, and reviewing diffs for the specific class of
   bug a framework/language is prone to (N+1 queries in an ORM, race conditions in async code,
   missing index on a new query pattern).
4. **Architecture/design patterns (SOLID, DDD, Hexagonal, CQRS, Event Sourcing):** Claude is
   strong at explaining trade-offs and spotting violations in existing code, but *you* own the
   architectural decision — treat its output as a well-informed second opinion, not the final call
   on a decision with real long-term cost.

**Common mistake:** asking for a whole feature in one shot on unfamiliar legacy code. Better: read
→ plan → implement in reviewable chunks → test, each as a separate turn you can check.

## Module 5 — Enterprise Development Workflow

Where Claude fits into a normal engineering week:

- **Legacy code comprehension:** paste/point Claude at a module, ask for a plain-English map of
  responsibilities and data flow before making changes — much faster than manual archaeology.
- **Feature dev:** requirements → clarify ambiguities → plan → implement → test, each a checkpoint.
- **Bug fixing / production RCA:** give it the actual error, logs, and relevant code — ask it to
  list *hypotheses ranked by likelihood* with what evidence would confirm/rule out each, rather
  than jumping to one fix.
- **Code/architecture/PR review:** use a standing review prompt (Module 9) that checks correctness,
  security, performance, and style consistently — removes reviewer fatigue/inconsistency.
- **Documentation & RFCs:** draft from an outline you provide; Claude is much better at expanding
  a clear outline into prose than inventing the outline's substance from nothing.
- **Estimation/sprint planning:** useful for breaking a vague ticket into concrete subtasks with
  relative sizing — not for guessing effort on things it has no grounding in.

**Anti-pattern:** using Claude output as a review substitute rather than a review *aid*. A human
still owns the merge decision, especially for security- and data-integrity-sensitive changes.

## Module 6 — Claude + GitHub

With a GitHub connector/integration, Claude can read real repos, issues, and PRs instead of pasted
snippets:

- **Repository/architecture understanding:** ask for a guided tour of an unfamiliar repo — entry
  points, key modules, how a request flows end to end.
- **PR review:** feed the diff plus surrounding context (not just the diff in isolation — diffs
  without context cause both false positives and missed issues).
- **Issue triage:** summarize, deduplicate, and suggest likely root cause/component for new issues
  in a large backlog.
- **Commit messages & release notes:** generate from the actual diff/commit range, then edit for
  voice — good first draft, not final copy for anything customer-facing.
- **Monorepos:** scope every request to the relevant sub-project explicitly; unscoped questions on
  a monorepo tend to produce shallow, generic answers.

## Module 7 — Claude Code

Claude Code is Anthropic's agentic coding tool — it runs in your terminal (and also has VS Code,
JetBrains, desktop-app, and web surfaces), with direct read/write access to your project files and
the ability to run commands, not just suggest text.

- **Install (current recommended path, verify at `docs.claude.com`):** the native installer —
  `curl -fsSL https://claude.ai/install.sh | bash` on macOS/Linux, with a corresponding
  installer for Windows — auto-updates and needs no Node.js. (An older npm-based install path
  exists in some older guides but has been superseded — check current docs rather than an old
  tutorial.)
- **Auth:** either an Anthropic Console API key, or your existing Claude Pro/Max/Team/Enterprise
  subscription, depending on how you already pay for Claude.
- **`CLAUDE.md`:** a project-root file of standing instructions (conventions, "always run tests
  before committing," known gotchas) that Claude Code reads automatically each session — the
  practical equivalent of onboarding a new hire. Keep it short (~100 lines); push large domain docs
  into separate files it reads only when relevant, so it doesn't burn context budget every session.
- **Core workflow:** it reads relevant files first, proposes a plan/diff, you review, it applies
  changes and can run your test suite — a tight read → plan → edit → verify loop rather than a
  single blind generation.
- **Sub-agents:** Claude Code can dispatch parallel sub-agents (e.g., one exploring auth code, one
  writing tests, one drafting docs) that each work in their own context and report back — keeps
  your main session's context clean on large tasks.
- **MCP servers, hooks, permissions:** extend it with external tools (Module 8), custom automation
  hooks around its actions, and fine-grained permission settings controlling what it's allowed to
  run/touch autonomously — important given it has real filesystem/command access.
- **Git integration:** works naturally with branches/diffs/`git diff` review — treat its commits
  like any other contributor's: reviewed before merge.

**Common mistake:** giving it broad, unscoped access and full autonomy on a production repo from
day one. Start with tighter permissions and a narrow task scope, and loosen as trust is earned.

## Module 8 — MCP (Model Context Protocol)

**What it is:** an open protocol standardizing how an LLM application connects to external tools
and data sources — think of it as a common plug shape so any MCP-compatible client (Claude
Desktop, Claude Code, others) can use any MCP-compatible server (GitHub, a database, Slack, a
custom internal tool) without bespoke integration code per pair.

**Architecture, at a glance:**
```
 Claude (client) ──MCP──▶ MCP Server ──▶ Real system
                          (exposes:      (GitHub API,
                           tools,         a DB,
                           resources,     Slack API,
                           prompts)       your own service)
```
- **Tools:** actions the model can invoke (e.g., `create_issue`, `run_query`).
- **Resources:** data the server can expose for the model to read (e.g., a file, a doc).
- **Prompts:** reusable prompt templates a server can offer to clients.

**Why it matters for enterprise:** instead of every team writing custom "Claude + our internal
system" glue code, you write one MCP server for that system once, and it works with any MCP
client. It's the same leverage as a standard API vs. n bespoke integrations.

**Security note:** an MCP server you connect gets whatever access you grant it — treat adding one
with the same scrutiny as granting a new service account API access (least privilege, review what
each tool can actually do, especially for anything with write access to production systems).

**Building your own:** at a high level, an MCP server is a small program exposing a defined set of
tools/resources over the protocol — commonly built with an SDK provided for this purpose. For
current SDK specifics and code samples, check the live MCP documentation rather than relying on a
static example here, since the protocol and SDKs are still evolving.

## Module 9 — Enterprise Prompt Library (starter templates)

Reusable, adaptable — fill in the bracketed parts per your stack:

**Code Review**
> Review this diff for correctness, security, and performance issues, in that priority order.
> For each issue: cite the exact line(s), explain the risk, and suggest a concrete fix. Do not
> comment on style unless it violates [your style guide]. Flag anything you're unsure about
> instead of guessing.

**Bug Investigation**
> Given this error/stack trace and the surrounding code, list your top 3 hypotheses for root
> cause, ranked by likelihood. For each, state what evidence would confirm or rule it out, and
> what you'd check next.

**Architecture Review**
> Evaluate this design against [our non-negotiables, e.g. must support 10x current load, must be
> horizontally scalable]. Identify the biggest risk, the biggest unknown, and one simplification
> that would reduce complexity without cutting a required capability.

**Security Review**
> Review this code/endpoint for [OWASP Top 10 relevant categories / your specific concerns].
> For each finding: severity, exploit scenario in one sentence, and minimal fix.

**API Design**
> Given these requirements, propose a REST/GraphQL contract. Include resource names, methods,
> status codes, and error shape. Flag any requirement that's ambiguous rather than assuming.

**Documentation**
> Turn this outline + these code references into docs for [audience]. Match the tone of
> [existing doc link/example]. Don't invent behavior not shown in the referenced code.

**RCA Template**
> Given [incident timeline, logs, changes deployed], write a blameless RCA: timeline, root cause,
> contributing factors, what monitoring would have caught it sooner, and 3 concrete follow-up
> action items with owners left as placeholders.

*(These are starting points — enterprise teams version these in a repo, refine wording based on
what actually produces good output, and track which version is "current.")*

## Module 10 — Real Enterprise Projects (simulation framework)

Rather than a fixed toy example, the durable skill is this loop, run once per project:

1. **Requirements** — have Claude help turn a vague ask into explicit, testable requirements;
   push back on anything ambiguous rather than assuming.
2. **Architecture** — propose 2–3 options with explicit trade-offs; pick one and record why.
3. **Implementation** — plan → chunked diffs → review each chunk, not one giant generation.
4. **Testing** — unit + integration, including edge cases and failure modes, not just the happy path.
5. **Deployment/CI-CD** — have it draft the pipeline config, but a human validates anything
   touching production credentials or infra state.
6. **Production issues/scaling/maintenance** — feed real incidents back through the RCA template
   above; feed learnings back into `CLAUDE.md`/prompt library so the same mistake isn't repeated.

When you're ready to actually run this end-to-end on a real (or realistic sample) project, say so

## Module 11 — Claude Best Practices

- **Context management:** keep system prompts stable, prune irrelevant history in long sessions,
  and prefer retrieval over dumping entire codebases/documents into context.
- **Token/cost optimization:** route simple tasks to cheaper/faster models; cache stable context
  (e.g., a large style guide) instead of re-sending it raw every call where the platform supports it.
- **Reusable workflows:** treat prompts as versioned artifacts (Module 3) with an owner and a
  changelog, not one-off chat messages.
- **Evaluation:** before trusting a prompt/workflow in production, run it against a small labeled
  set of past examples and check output quality — the same discipline as testing code.
- **Security/privacy/compliance:** never paste real customer PII/secrets into prompts unless the
  environment (enterprise data handling terms, your org's approved tooling) is explicitly cleared
  for it; treat an MCP connector's access scope the same way you'd treat a new service account.
- **Model selection:** match model tier to task difficulty and latency/cost requirements — verify
  current model names/pricing at `docs.claude.com` rather than assuming last year's lineup still
  applies.

## Module 12 — Advanced Topics

- **Agents & multi-agent systems:** an "agent" here means Claude given a goal, tools, and the
  autonomy to decide its own steps (vs. a single Q&A turn). Multi-agent setups (like Claude Code's
  sub-agents) split a large task across parallel workers with isolated context, then merge results
  — useful specifically when a task is large enough that one context window would get noisy.
- **RAG (Retrieval-Augmented Generation):** instead of relying on the model's trained knowledge,
  you retrieve relevant documents/data at request time and inject them into context — this is how
  "memory" and "knowledge base" features are actually built under the hood.
- **Tool use:** the mechanism by which a model can call external functions (search, code
  execution, your internal APIs) mid-response instead of only generating text — the foundation
  everything in Modules 2, 7, and 8 is built on.
- **Human-in-the-loop:** for any agentic workflow with real-world side effects (deploys, emails,
  payments), keep an explicit human approval step before the irreversible action — autonomy and
  blast radius should scale together, not independently.
- **Evaluation frameworks:** systematic, repeatable testing of prompts/agents against a benchmark
  set, tracked over time as you change prompts or models — without this, "it seems better" is just
  a feeling, not a measurement.
